# Roadmap: food entry, nutrition data, clinician statistics, clinician assistant

Written 2026-11-26 after the forest-and-sage redesign (#6), Next meal (#7) and the rules follow-up (#10)
shipped. Each step is meant to be one PR: small, tested, and checked on a phone and a desktop before merge.
Steps marked **Decision** need a human (founders or a clinician) before work starts.

The order matters: phases 1 to 3 make the app useful without any AI. Phase 4 is the gate that must be
passed before an AI sees real patient data. Phase 5 builds the assistant on top of the statistics from
phase 3.

---

## Phase 1: adding a food in seconds

Goal: a parent logs a full meal in under 15 seconds, with one thumb, without typing most of the time.

1. **Measure the baseline.** Count the taps and seconds to log a typical dinner today, on a phone. This is
   the number to beat. Write it in the PR.
2. **The family's foods first.** Search shows the family's own recent and frequent foods before anything
   else, ranked by how often they were served at this meal. It works offline and needs no API.
   The pieces exist (`foodItems`, `sameAsYesterday`); this step unifies them into one search box.
3. **"Usual meals".** Save a whole meal as a usual (for example "school-day breakfast") and log it in one
   tap, then adjust. Stored under the parent's own node. Needs a rules entry and a rules test.
4. **New foods from USDA.** When the family's list has no match, show USDA results from the Worker's existing
   search. Picking one adds it to the family's foods, so it's local from then on.
5. **Portions without numbers.** Keep the simple fractions (¼, ½, ¾, all) for parents. No grams or calories
   on parent screens (`appMode.hideNutritionNumbers`).
6. **Decision:** photo or voice entry. Both are faster but send meal data to another vendor (a new PHI
   sink under AGENTS.md rule 5), so they wait for phase 4 unless done fully on the device.

## Phase 2: current nutrition data

Goal: every logged food has nutrition values from a maintained source. Clinicians can see them; parents
don't, unless a clinician turns that on.

1. **One lookup path.** Route all nutrition lookups through the Worker's USDA FoodData Central endpoint.
   Retire `src/data/nutritionDb.json` and `commonFoods.js`, which are outdated, keeping them only as an
   offline fallback until step 3 lands.
2. **Store the result on the food, once.** When a food is added, save its USDA id, the matched name and the
   core values on `foodItems/{id}`, with the date fetched. Meals point at foods, so each food is looked up
   once per family, not every time it's eaten. The hooks exist (`setFoodNutrition`, `resetFoodNutrition`).
3. **Worker caching and limits.** Cache USDA responses in the Worker (Cloudflare KV) and rate-limit per
   user, so the free USDA quota holds as families are added. The key stays in the Worker.
4. **Decision:** packaged foods. USDA's branded data covers a lot of US products. Open Food Facts adds
   barcodes, but its data is crowd-sourced. Pick one with a dietitian.
5. **Show numbers only where they belong:** clinician views, and a parent view only if the clinician enables
   it for that family.

## Phase 3: turning meals into statistics for clinicians

Goal: before a session, a clinician sees in under a minute how the week went and what changed, and every
number can be traced to the meals behind it.

1. **Decision (with a clinician): the metric list.** Draft to react to:
   - meals completed, partly finished, refused and not served, by meal and by day;
   - refusals by meal, time of day and weekday;
   - distress before and after meals, as a trend;
   - challenge foods offered and how each went;
   - meals not logged;
   - meal timing drift;
   - for clinicians only, estimated energy ranges from phase 2 data.
2. **A pure statistics module.** Put the agreed metrics in `src/lib/clinicianStats.js`, with tests next to it.
   It's deterministic: the same meals always give the same numbers, and each number lists the entries
   behind it. It builds on what exists (`sessionPrep.js`, `weekStats.js`, `anomalyDetection.js`, `trends.js`).
3. **The clinician dashboard, redesigned.** In the forest-and-sage system:
   - the week at a glance;
   - 4 to 8 week trends;
   - "worth talking about" items;
   - the session plan box that sends to the family (as in the canvas mock-up).
4. **Export for the session.** A printable page or PDF of the week, for clinicians who take notes on paper.
5. **Decision:** whether parents see any of this. The current answer is no scores for parents, so they get
   only the plain sentences on the Week screen.

## Phase 4: the gate before any AI sees patient data

Required by AGENTS.md ("never see identifiable data without a signed BAA") and `COMPLIANCE.md`.

1. **Decision:** storage. Stay on Firebase Realtime Database or move. This decides which BAA you need.
2. Sign the Google Cloud / Firebase BAA (`COMPLIANCE.md` item 1).
3. Sign a BAA with the model provider, or use a provider or hosting option that offers one.
4. Strip identifiers before anything goes to a model: no names, emails or family codes; dates shifted
   or relative. Done in the Worker, with tests.
5. Audit log of every assistant request: who asked, which family, when. No meal content in the log.

## Phase 5: the clinician assistant

Goal: a clinician asks things like "is this pattern of refusing breakfasts usual at week 6?" and gets a short,
sourced, clearly labelled suggestion to review, never a diagnosis or a prescription.

1. **Recommendation: don't train a model from scratch.** It costs a lot, needs patient data you don't
   have consent for, and still makes things up. Start with an existing model behind the Worker that:
   - gets its numbers only from the phase 3 statistics module (as tools it calls, never computing them itself);
   - gets its knowledge only from a library of vetted clinical sources (retrieval), and cites them;
   - labels every answer as a suggestion to review, with the evidence next to it (AGENTS.md).
2. **Build the source library.** Collect the guidelines a clinician picks, for example eating-disorder
   medical-care guidelines and FBT treatment manuals. **Decision:** check licensing before storing any text.
3. **Write the evaluation set first.** With clinicians, write 50 to 100 real questions with good answers,
   plus safety tests (self-harm, purging, requests for calorie targets). The assistant ships only if it
   passes. Prompts are reviewed like code, with a test or a before-and-after example (AGENTS.md).
4. **Pilot.** Read-only for 1 or 2 clinicians, on de-identified data, with a feedback button on every answer.
5. **Fine-tune later, only if the evaluation shows a gap** that retrieval and prompting can't close. That
   needs consented, de-identified examples (clinicians' rated answers from the pilot are the best source).
   **Decision:** which provider or open model, and where it runs (a BAA again).
